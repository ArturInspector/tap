# Backend Stack

## Выбор: Python (FastAPI)

### Почему Python:

1. **Уже есть кодовая база**
   - agent-registry на FastAPI
   - merchant-backend на FastAPI
   - Переиспользуем модели, схемы, логику TAP

2. **Библиотеки интеграций**
   - `ShopifyAPI` - официальная Python библиотека
   - `python-amazon-sp-api` - SP-API клиент
   - `woocommerce` - REST API клиент
   - `httpx` - уже используется для TAP

3. **Скорость разработки**
   - Хакатон = 24-48 часов
   - FastAPI = быстрый прототип
   - Type hints = меньше багов
   - Pydantic = валидация из коробки

4. **TAP Protocol**
   - Уже реализован на Python в текущем проекте
   - Подпись запросов, верификация - готовые модули

## Задача бэкенда

Бэкенд решает следующие задачи:

1. **Интеграция с платформами продаж**
   - Подключение к Shopify, Amazon, WooCommerce через их API
   - Создание витрин для мерчантов
   - Синхронизация товаров между платформами
   - Обработка заказов через webhook

2. **Автоматическая настройка TAP**
   - Генерация криптографических ключей для мерчантов
   - Регистрация агентов в Agent Registry
   - Генерация TAP подписей для запросов от AI агентов
   - Верификация подписей входящих запросов

3. **Проксирование и маршрутизация**
   - Proxy/Gateway для перехвата запросов от платформ
   - Автоматическое добавление TAP подписей к запросам
   - Проксирование запросов к мерчантам
   - Логирование для аналитики

4. **Автоматизация бизнес-процессов**
   - Синхронизация инвентаря между платформами
   - Автоматическая обработка заказов
   - Управление товарами и ценами
   - Интеграция с платежными системами

5. **Аналитика и мониторинг**
   - Сбор данных о заказах по платформам
   - Разделение заказов от AI агентов и обычных пользователей
   - Статистика конверсии по каналам
   - Метрики выручки и производительности

## Принципы разработки

### SOLID

**S - Single Responsibility Principle (Принцип единственной ответственности)**
- Каждый класс/функция решает одну задачу
- Модели только описывают данные
- Сервисы только выполняют бизнес-логику
- Роуты только обрабатывают HTTP запросы

**O - Open/Closed Principle (Принцип открытости/закрытости)**
- Код открыт для расширения, закрыт для модификации
- Новые интеграции добавляются через базовый класс, без изменения существующего кода
- Использование интерфейсов и абстракций

**L - Liskov Substitution Principle (Принцип подстановки Лисков)**
- Подклассы должны заменять базовые классы без изменения поведения
- Все интеграции (Shopify, Amazon) должны работать через единый интерфейс

**I - Interface Segregation Principle (Принцип разделения интерфейса)**
- Интерфейсы должны быть специфичными, а не общими
- Клиенты не должны зависеть от методов, которые они не используют

**D - Dependency Inversion Principle (Принцип инверсии зависимостей)**
- Зависимости должны быть на абстракциях, а не на конкретных реализациях
- Использование dependency injection

### Дополнительные принципы

**DRY - Don't Repeat Yourself**
- Избегать дублирования кода
- Выносить общую логику в функции/классы
- Переиспользовать существующие модули TAP

**KISS - Keep It Simple, Stupid**
- Простота важнее умности
- Избегать сложных абстракций, если не нужны
- Понятный код лучше умного кода

**YAGNI - You Aren't Gonna Need It**
- Не добавлять функциональность "на будущее"
- Реализовывать только то, что нужно сейчас
- Рефакторинг делать когда появилась реальная потребность

## Правила написания кода

### Общие правила

1. **Итеративная разработка**
   - Пиши код небольшими шагами
   - Сначала простая рабочая версия, потом улучшения
   - Не пытайся сделать всё идеально с первого раза
   - Тестируй каждое изменение

2. **Упрощение**
   - Если код сложный - упрости его
   - Избегай сложных конструкций без необходимости
   - Предпочитай явное неявному
   - Простота важнее оптимизации (пока нет проблем производительности)

3. **Поддержка**
   - Код должен быть понятен через месяц
   - Используй понятные имена переменных и функций
   - Комментируй только сложную логику или неочевидные решения
   - Документируй публичные API

4. **Стиль кода**
   - Используй type hints везде
   - Следуй PEP 8
   - Функции должны быть короткими (до 50 строк)
   - Классы должны быть маленькими (до 200 строк)

5. **Обработка ошибок**
   - Используй исключения для обработки ошибок
   - Логируй ошибки с контекстом
   - Возвращай понятные сообщения об ошибках клиентам
   - Не проглатывай исключения без логирования

6. **Тестирование**
   - Пиши тесты для критичной логики
   - Моки для внешних зависимостей
   - Интеграционные тесты для API endpoints

7. **Безопасность**
   - Не храни секреты в коде (используй env переменные)
   - Валидируй все входящие данные через Pydantic
   - Используй параметризованные запросы для SQL
   - Проверяй права доступа перед операциями

### Структура кода

- **Модели** - только структура данных, без бизнес-логики
- **Схемы** - Pydantic модели для валидации входящих/исходящих данных
- **Роуты** - тонкий слой, только HTTP обработка и валидация
- **Сервисы** - вся бизнес-логика
- **Интеграции** - работа с внешними API, абстракция через базовый класс

### Именование

- Функции: глаголы в нижнем регистре (`create_merchant`, `process_order`)
- Классы: существительные в CamelCase (`ShopifyIntegration`, `MerchantService`)
- Константы: UPPER_SNAKE_CASE (`MAX_RETRY_COUNT`)
- Переменные: snake_case (`merchant_id`, `order_data`)
